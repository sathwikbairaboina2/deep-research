# How does SQLite WAL mode affect reader and writer concurrency?

_Status: done. 18 of 18 proposed claims verified; 0 rejected by the citation verifier._

In WAL mode, readers and writers can operate concurrently because readers do not block writers and writers do not block readers [^1]. This is achieved by having the writer append changes to a separate file while readers continue operating from the original unaltered database file [^2]. Unlike rollback journal mode, where writers block readers during write and commit phases, WAL mode structures locks differently to allow concurrent readers during a write [^3]. Specifically, in classic journal mode, a writer obtains locks that prevent other writers and sometimes readers, whereas in WAL mode, this restriction is removed for readers [^4]. While readers and writers can run simultaneously, SQLite WAL mode serializes write operations, meaning only one transaction can hold the write lock at any given moment [^5]. Consequently, a writer and any number of readers can be active simultaneously, with each reader seeing a consistent snapshot of the database as it existed at the start of their transaction [^6]. This snapshot isolation ensures that each reader sees a consistent view of the data [^7]. Long-running read operations do not prevent writers from proceeding with their transactions [^8]. However, long-running read transactions can prevent SQLite from safely removing old WAL frames, which may lead to huge WAL files and slower checkpoints [^9]. The coordination of these concurrent accesses is managed by the pager module, which ensures ACID properties and coordinates access between separate threads or processes [^10]. This coordination relies on file locks implemented by the VFS layer, using lock states such as SHARED, PENDING, and EXCLUSIVE to govern read and write permissions [^11]. WAL mode requires shared memory for coordination on many operating systems and produces .wal and .shm files alongside the main database file [^12]. Due to this reliance on shared memory, WAL mode is not suitable for network filesystems like NFS or SMB because these systems do not provide reliable shared memory support [^13]. The official SQLite locking documentation describes the locking mechanism for the older rollback-mode transaction mechanism, while locking for the newer write-ahead log (WAL) mode is described in separate documentation [^14].
